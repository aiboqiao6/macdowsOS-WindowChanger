## 失败记录

### WPF 导入表解析崩溃

旧引导 `185119447be3` 的 x64 Debug/Release 在真实 WPF 回归中崩溃，异常 C0000005 后产生 C000041D。原生调用栈指向 `AcquireReads` 的导入符号比较：64 位进程中可以映射 PE32 格式的托管程序集，按当前进程的 PE64 头及 thunk 宽度解释这些映像会把错误地址当作导入名称。新 `pe-imports.h` 先验证 Machine、OptionalHeader magic、大小及目录，再使用有界可读性检查枚举本机格式的普通/延迟导入；不解析其他格式或缺失名称表的已解析 IAT，也保留未解析延迟导入及第三方 hook。

`pe-imports-tests.cpp` 的 18 项检查覆盖对立 PE 格式、Machine 不匹配、混合宽度坏 thunk、不可读页、越界、无终止符、延迟导入及 IAT 对齐。`45abea09d2b7` 的四种构建配置均通过这些检查。修复后的 Debug WPF 两个实际测试窗口正常关闭，退出码为 0；`tests.cpp` 同时增加退出码断言，避免把“进程已退出”误算成正常退出。完整 CTest 结果仍需单独完成。

### WinUI 文本和主题

早期正式 Host 使用 Session 默认 Native，日志为 adapter=1，未计入通过；改为显式 Automatic，并在附加后检查 288。实际控制器验证第一轮错误地把主控制器 HWND 当成租约 owner；正式结构由其守护 Host 持有租约，修正为核验 Host.Parent 与 Host 进程路径，保留初次失败。

最终 Release 文本组首轮整窗比较相差 3 个 TextBox 圆角边缘像素，各通道灰度相差 1，位于 (243,259)、(242,260)、(242,490)。编辑、焦点、历史和完整几何断言均通过，但整组仍判失败。独立纯原生重放三次均为 08E138A43B70D44CBF64D51C90964F8B30E5EE14E6BE4C9B3763B41D5E5A151E，未复现该次差异，不能将其原因确定为原生波动。失败图 9FD077598E46B4A27A338C8A7C430BE8B085E8EEE39D1925F2C44D25C300FF3D 与原日志保留。后续仍要求整图精确匹配；不能用重跑通过抹去该初始失败。

## 追加复核与就绪检查

`c1686dd13da8` 的 x64 Release/Debug 完整 CTest 各 22/22、Win32 Release 12/12 通过。Win32 Debug 首轮为 10/12：两项标题测试分别失败 8、12 个断言，旧截图的标题底部存在深色覆盖带。相同二进制独立复核分别 47/47、46/46；这不能抹去首轮失败或单独证明其原因。标题截图检查现增加前台身份、上层窗口遮挡检查及 DwmFlush，受遮挡的屏幕不再作为有效标题像素来源。

`c1686dd13da8` 原始 fixture 的 Release 和 Debug 完整文本矩阵各通过 880 项；Debug 此前也曾出现完全相同的三个圆角像素差异。因此仍没有把主题 PostMessage 合并更新认定为像素问题的最终修复。失败后可用独立自有窗口诊断器读取浮点几何、合成 Visual 和状态；这些 getter 可能创建合成 Visual，只用于保留原失败后的诊断，不能替换失败图或算作完全不注入的原生对照。
